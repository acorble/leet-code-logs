# LeetCode の問題を記録する

ユーザーが解いた問題を `problems/` に記録する。以下を順に実行すること。

## 最優先のルール

問題 README の `## 考えたこと / アプローチ` の**中身は絶対に書かない**。
下書き・要約・清書・補完・追記、どれもしない。ここは本人が手で書く欄。
Claude がしてよいのは `### N 回目` という**空の見出しを用意することだけ**で、
それはスクリプトが自動でやる。既存の記述の書き換え・削除・整形もしない。
（ユーザーが明示的に「そこに書いて」と言った場合だけ例外。）

## 0. 初回か、解き直しかを判別する

まず `problems/*/` に同じ番号のディレクトリが既にあるか確認する
（`ls problems/*/ | grep <4桁番号>` など）。

- **無い** → 初回。1. 以降を実行する
- **ある** → 解き直し。「解き直し」の節（下）へ進む

## 0.5. 情報を集める

必要なのは **問題番号・タイトル・カテゴリ・難易度・解答コード** の 5 つ。

- ユーザーが番号だけ言った場合や、コードを貼らずに「解いた」とだけ言った場合は、
  足りない情報（特に解答コード）をまとめて 1 回で聞く。推測で書かない。
- カテゴリは次の 7 つから選ぶ。適切なものを提案し、迷う場合のみ確認する:
  `arrays-hashing` / `two-pointers` / `stack` / `binary-search` /
  `sliding-window` / `linked-list` / `trees`
- 問題文の Example（入力と期待される出力）も聞くか、コードから妥当なケースを起こす。
- **自力**（◎ 何も見ずにすんなり / ○ 何も見ずに解けたが時間がかかった /
  △ ヒント・解説・過去の解答を見た / × 解けなかった）。次に解き直す日の計算に使う。
  ユーザーの話から判断できればそれを使い、分からなければ他の不足情報と一緒に聞く。
  「結果」(AC など) とは別物。AC でも解答を見ながらなら △

## 1. 雛形を作る

```bash
python scripts/new_problem.py <番号> "<タイトル>" -c <category> -d <easy|medium|hard> --recall <◎|○|△|×>
```

手動で `mkdir` しないこと。ディレクトリ名・テストファイル名の規約はこのスクリプトが担保している。
実行すると問題の README がエディタで開く。ユーザーがその場で「考えたこと」を
書けるようにするためなので、**`--no-open` は付けないこと**。
すでに存在する場合はエラーになる。その場合は解き直しなので「解き直し」の節へ。

## 2. solution.py にコードを入れる

ユーザーが貼ったコードを **そのまま** 入れる。docstring（番号・タイトル・URL）は雛形のものを残す。
型ヒントの付与や軽微な整形は行ってよい。

未完成のコード・間違っているコード・途中で詰まったコードも、そのまま記録の対象とする。
勝手に直さないこと。直すのは、ユーザーが明示的に頼んだときだけ。
気づいた問題点は、記録を終えたあとに 7. の報告として伝える。

## 3. テストを書く

生成されたテストファイル（`test_<番号>_<スラッグ>.py`）に問題文の Example を写す。

```python
def test_example_1(solution):
    assert solution.Solution().twoSum([2, 7, 11, 15], 9) == [0, 1]
```

- `solution` フィクスチャが同じディレクトリの `solution.py` を読み込む。import は書かない
- Example が複数あれば `test_example_2`, `test_example_3` と足す
- 空配列・1 要素・見つからないケースなど、エッジケースを 1〜2 個加える

## 4. テストを走らせる（任意・記録を止めない）

```bash
./.venv/bin/python -m pytest problems/<category>/<dir>
```

`.venv` が無ければ作る:
`python3 -m venv .venv && ./.venv/bin/pip install -r requirements.txt`

Windows では `.venv/bin/` が `.venv/Scripts/` になる（`./.venv/Scripts/python.exe -m pytest ...`）。
スクリプトの実行も `.venv` の python を使ってよい。

**テストが落ちても、そこで作業を止めないこと。** 未完成・不正解のコードを
そのまま残したい場合があるため、テストはコミットの条件ではない。
落ちた場合は、そのまま 5. 以降を続けて記録を完了させ、7. の報告で
「どのケースが落ちたか」を伝える。テストの期待値を通すために書き換えないこと。

ユーザーが「まだ途中」「動いてない」と言っている場合は、テストの実行自体を
省略してもよい。その場合は問題の README にその旨を一行残す。

## 5. 問題の README を埋める

雛形のコメント行を、実際の内容に置き換える。ただし埋めてよい節と、そうでない節がある。

**Claude が書く節:**

- **問題の要約**: 1〜3 行
- **計算量**: 時間・空間を実際のコードから算出する
- **学び・再利用できるパターン**: 次に似た問題が来たとき思い出せる形の一般化。
  関連する問題があれば相対パスでリンクする
- **復習ログ**のメモ列: ユーザーが話した内容の範囲で短く
- **次回やること**: 本人も Claude も書いてよい節。`- [ ] ...` の箇条書きで、
  次に解き直すときに試すこと（別解・計算量の改善・解説を見る など）を書く。
  ユーザーが「〜でも解く」「〜を見る」と言ったもの、学びの節で挙げた改善点を入れる。
  ここに書いたものが REVIEW.md に載る

**Claude が書かない節:**

- **考えたこと / アプローチ**: 本人の欄。`### N 回目` の空見出しがあるだけの状態で残す。
  中身は絶対に書かない。報告のときに「ここは自分で書いてください」と一言添える。

## 6. 一覧を更新してコミット

```bash
python scripts/update_index.py   # ルート README の一覧 + PROGRESS.md + REVIEW.md
git add -A && git commit -m "<番号>. <タイトル>"
```

`PROGRESS.md` は NeetCode 150 の進捗表、`REVIEW.md` は解き直しの予定表で、
どちらも `problems/` から自動生成される。**手で ✅ を付けたり編集したりしないこと。**

テストの成否にかかわらずコミットする。未完成なら
`git commit -m "<番号>. <タイトル> (WIP)"` のように印を付ける。

## 7. 報告する

作ったディレクトリ、テスト結果（走らせた場合）、README に書いた要点を短くまとめる。
テストが落ちた・コードに問題があると気づいた場合は、ここで初めて具体的に指摘する。
解法について補足できる観点（別解、関連問題、計算量の改善余地）があれば 2〜3 行添える。

# 解き直し（2 回目以降）

同じ問題を何度も解くのはこのリポジトリの主目的なので、上書きせず必ず履歴として残す。

## A. 前回のコードを退避する

```bash
python scripts/new_attempt.py <番号> --recall <◎|○|△|×> --result <AC|WA|TLE|giveup> --minutes <所要時間> --note "<ひとこと>"
```

これで前回の `solution.py` が `attempts/<日付>.py` にコピーされ、
README の復習ログに今回の行が追加され、README がエディタで開く。
**手でファイルを移動しないこと。** `--no-open` は付けないこと。

**`--recall` は解き直しでは特に重要**（次に解く日がこれで決まる）。
ユーザーの話から判断できなければ聞く。前回のコードや解説を見ながら解いたなら、
AC でも △。`--result` `--minutes` `--note` はユーザーが言っていない場合は省略してよい
（後から README を直接編集して埋められる）。所要時間は上達の記録として価値があるので、
話に出ていれば必ず入れる。

## B. 今回のコードを solution.py に上書きする

`solution.py` には常に最新の解答が入る。前回のコードは attempts/ にあるので失われない。

## C. 前回と比べる

```bash
diff problems/<category>/<dir>/attempts/<日付>.py problems/<category>/<dir>/solution.py
```

差分を見て、**前回から何が変わったか** を具体的に述べる。ここがこのリポジトリの価値の中心。

- アプローチ自体が変わったか（総当たり → ハッシュ、など）
- 計算量が改善したか
- 前回詰まった箇所を今回は自力で越えられたか
- 逆に前回のほうが良かった点はないか

## D. README を更新する

- 復習ログの行に、今回の気づきをメモとして書く（1 行で簡潔に）
- 「考えたこと / アプローチ」には `### N 回目` の空見出しが自動で足されている。
  **中身は書かない。既存の回の記述にも触らない。**
- 「学び・再利用できるパターン」は上書きせず追記する。前回の記述を消さない
- 解法が変わった場合は「計算量」を更新する
- 「次回やること」のうち今回済んだ項目は行ごと消す（履歴は復習ログと学びの節に残る）。
  新しく出てきた課題があれば足す

## E. テスト・一覧更新・コミット

テストは任意（落ちても止めない）。最後に:

```bash
python scripts/update_index.py
git add -A && git commit -m "<番号>. <タイトル> (<N>回目)"
```

報告では、C で見つけた前回との差分を必ず伝える。
「考えたこと」の欄が空であることも伝え、本人に書いてもらう。
