## 計算量

- 時間: **O(n)** — 内側の while も含め、各文字を高々 1 回しか見ない
- 空間: **O(1)** — 文字列を作り直さず、添字だけで処理する

**これが最適**。`[c for c in s if c.isalnum()]` と作り直す書き方は簡潔だが、
O(n) の追加メモリを使う。

## 学び・再利用できるパターン

- **両端から中央へ寄せる 2 ポインタ**。回文判定の基本形。
  スライディングウィンドウ（片側から伸ばして片側を詰める）とは向きが違い、
  **左右から同時に内側へ**進む
- **飛ばす処理を内側の while に切り出す**。「見るべき文字まで進める」を
  外側のループと分けることで、比較のロジックが 1 行で済んでいる
- 内側の while が入れ子になっていても、`left` は増えるだけ・`right` は減るだけなので、
  **全体では各文字を 1 回しか見ない**。見た目の入れ子と計算量は一致しない
- 内側のループにも `left < right` の条件を入れているのが重要。
  これが無いと、英数字が無い文字列で添字が範囲外へ飛ぶ

### 文字列を作り直さないのが効いている

```python
cleaned = [c.lower() for c in s if c.isalnum()]   # 簡潔だが O(n) メモリ
return cleaned == cleaned[::-1]
```

こちらのほうが短く書けるが、**元の文字列と同じ大きさの配列を作る**。
この解答は添字だけで処理していて追加メモリが要らない。
「作り直す」か「その場で見る」かの分かれ道は
[206](../../linked-list/0206-reverse-linked-list) の 1 回目 → 2 回目と同じ構図。

正しさはランダム 2,500 パターン（回文になりやすい入力を含む）で確認済み。

### 2 回目（7/19）: 同じ考え方を、より短く書いた

アルゴリズムは 1 回目と同じ（両端から寄せる 2 ポインタ、英数字以外は飛ばす）。変わったのは書き方だけ。

```python
# 1 回目: 条件を中で判定して break
while left < right:
    if s[left].isalnum():
        break
    else:
        left += 1

# 2 回目: 「飛ばす条件」を while の条件そのものにした
while l < r and not s[l].isalnum():
    l += 1
```

「〜の間は進める」を `while 条件:` に直接書くと、`if` / `break` / `else` が要らなくなる。
1 回目の学びで「重要」と書いた内側の `l < r` も、2 回目でちゃんと残っている。
計算量は変わらず、時間 O(n)・空間 O(1)。

### 3 回目（8/16）: 内側の `l < r` が抜けて、記号だけの文字列で落ちた

2 回目との違いは、内側の 2 つの `while` から `l < r and` が消えたことだけ。

```python
while not s[l].isalnum():   # l < r が無い
    l += 1
```

英数字が 1 つも無い文字列では、`l` が止まる場所がないまま右端を越えて、
`s[l]` が `IndexError: string index out of range` になる。

```
s = ".,"   l=0 '.' → l=1 ',' → l=2 → s[2] は存在しない → エラー
```

テストでは `test_symbols_only`（`".,"`）と、記号の多いランダムな入力の 2 件が落ちる。

1 回目の学びに「内側のループにも `left < right` の条件を入れているのが重要。これが無いと、英数字が無い文字列で添字が範囲外へ飛ぶ」と
書いたとおりのことが起きている。
外側の `while l < r` があるので安全に見えるが、**内側のループが回っている間は外側の条件は確かめられない**。
内側で添字を動かすなら、内側にも止まる条件が要る。

[20. Valid Parentheses](../../stack/0020-valid-parentheses) の 2 回目（空の Stack から `pop()` してエラー）と同じ日に、
同じ種類のミス（**添字や pop を進める前に、まだ範囲内かを確かめていない**）をしている。

### 4 回目（8/16、同じ日の書き直し）: `l < r` を戻して AC

3 回目のエラーを、内側の 2 つの `while` に `and l < r` を足して直している。

```python
while not s[l].isalnum() and l < r:
    l += 1
```

2 回目は `l < r and not s[l].isalnum()` と、**`l < r` が先**だった。4 回目は**後**になっている。
`and` は左から評価するので、4 回目では `l < r` を確かめる前に `s[l]` を読む。

それでも今回は落ちない。`l` は外側の条件 `l < r` から始まり、内側で 1 ずつ進んで `l == r` で止まるので、
`s[l]` を読む時点の `l` は最大でも `r`（範囲内）にしかならないから。

ただ、これは「たまたま範囲内に収まる」ことに頼っている。
**範囲の確認は、その範囲を使う式より先（左）に書く**のが安全な習慣
（[20](../../stack/0020-valid-parentheses) の 3 回目の `stack != [] and stack.pop() == '('` も、確認が先になっている）。

| 2 回目（7/19） | `l < r and not s[l].isalnum()` | - |
