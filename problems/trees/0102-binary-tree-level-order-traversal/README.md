## 問題の要約

二分木を上の階層から順に走査し、階層ごとに値をまとめたリストのリストを返す。

### 1 回目

<!-- 最初に思いついた方針、詰まった点、気づき -->
解けた。BFSで層ごとに走査しながら、層ごとに管理するlistにvalをappendしていって、層の中のNode全部に対して処理が終わったらlistをList[List]にappendする形で対応。それをwhile文で中身なくなるまで回す。
結果はBeats100%だったのでTime Complexityベストだったんだろうなという感じだが、層ごとの走査のなかでlist.pop(0)してるのでパフォーマンス悪いだろうなと思いながらまあいいやと思って解いたので驚きだった。（なんで？）

→ LeetCodeのテスト上、たまたまノード数が少なかったからパフォーマンス良いように見えただけ。全然良くはないので解き直す。BFSの定石はstackではなくdequeを使う。
問題の本質は「層ごとの区切り」をどうするか。len(stack)を使った区切りを自力で思いついた点は評価ポイント。

### 2 回目
1回目の反省を活かしてdequeを使って解き直せた。BFSを使って解く場合はdequeを使うことが定石だと学んだ。覚えておく。今までDFSばっか解いてきたがBFSも板についてきたかも。
また1回目のときから変わった点として、Null(None node)の扱い方。正直タイムパフォーマンス的には1回目のアプローチの方がよい。つまり、子がNoneなら最初からdequeに加えないというアプローチ。2回目は少し変えて、子がNoneでもとりあえずdequeに加えて走査してしまう、ただしpopleft()したときにNoneじゃないことを毎回確かめる。こうすると走査数増えるからパフォーマンス落ちるのと、最後Noneだけの層でもfor文の走査が走ってしまうので[]という空配列が戻り値に含まれてしまう。なのでif valuesByLevel:というチェックを加えた。
今まで解いてきたBFSだとdequeを使ってNodeを走査して、最後まで走査しきってしまうアルゴリズムだったが、level（層）ごとに何か処理をする、というケースがこの問題の本質だと思った。BFSの練習に良い。定期的に解きたい問題。

## 計算量

| 回 | 時間 | 空間 | |
| --- | --- | --- | --- |
| 1 | O(n × 最大幅) | O(n) | `list.pop(0)` が O(n) のため |
| 2 | **O(n)** | O(n) | `deque.popleft()` は O(1) |

2 回目は None も queue に入れるので、queue に入る要素数は最大 2n 程度になる。
オーダーは変わらないが、定数倍は 1 回目よりわずかに増える。

## 学び・再利用できるパターン

- **レベルごとに区切る BFS**: ループの先頭で `len(queue)` を控えておき、その回数だけ
  取り出す。これで「今の階層のノードだけ」を処理できる。
  階層を意識する木の問題（[199. Right Side View](../0199-binary-tree-right-side-view),
  103. Zigzag Level Order など）はすべてこの形に乗る
- 先頭から取り出すなら `list.pop(0)` ではなく `collections.deque` の `popleft()`。
  list の pop(0) は残り全体をずらすので O(n) かかり、BFS 全体では O(n × 最大幅) になる

### `pop(0)` で Beats 100% だった件（実測）

完全二分木（幅が最大 = pop(0) に最も不利）で計測した結果:

| ノード数 | `list.pop(0)` | `deque.popleft()` | 差 |
| --- | --- | --- | --- |
| **2,000**（この問題の制約） | 0.4ms | 0.2ms | 1.9 倍 |
| 20,000 | 15.0ms | 1.5ms | 10 倍 |
| 200,000 | 1,579ms | 13ms | 120 倍 |
| 1,000,000 | 39,076ms | 68ms | 579 倍 |

- この問題はノード数 2000 以下。その領域では差が 0.2ms しかなく、
  Python のループ自体の overhead に埋もれて見えない。`pop(0)` の中身は C の memmove で、
  「要素をずらす」処理としては十分速い。**O(n²) でも n が小さければ表に出ない**
- LeetCode の実行時間は測定ノイズが大きく、同じコードでも Beats 60% ～ 100% で揺れる。
  **Beats 100% は最適だった証明にはならない**
- ただし制約が 10^5 になった瞬間に TLE する。問題ごとに判断するより、
  BFS では常に deque を使うほうが事故らない。変数名も自然に `queue` になり、
  「FIFO のつもりで書いている」という意図がコードに出る

→ 次に解き直すときは `deque` + `popleft()` で書く。
   `len(queue)` で層を区切る核心部分は変わらない

### 2 回目で変わったこと

- `deque` + `popleft()` に変更 → 時間計算量が O(n × 最大幅) から **O(n)** になった
- 変数名が `stack` → `nodeQueue` になり、FIFO で使っている意図がコードに出た
- **None の扱い方が変わった**。1 回目は「入れる前に None かどうか見る」、
  2 回目は「入れておいて、取り出したときに見る」。どちらも正しく、それぞれ性質が違う:

  | | 1 回目（入れる前に判定） | 2 回目（取り出してから判定） |
  | --- | --- | --- |
  | queue に入る数 | 実ノード数 n | 最大 2n（葉の下の None も入る） |
  | `root=None` の扱い | 冒頭の早期 return が必要 | 早期 return 不要。自然に `[]` が返る |
  | 空レベルの判定 | 不要 | `if valuesByLevel` のガードが必要 |

  早期 return が消えた代わりに、末尾にガードが増えた形。どちらか一方は必ず要る。
  木が大きいほど「入れる前に判定」のほうが queue が小さくて済む
