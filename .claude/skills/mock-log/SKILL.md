# 英語で話した記録を残してレビューする

記録は 2 種類ある。どちらも `problems/<category>/<dir>/english/<日付>-<mock|solo>.md` に保存する。

| | mock（人との mock interview） | solo（一人での説明練習） |
| --- | --- | --- |
| 何をしたか | 面接官役の前で、その場で問題を解きながら英語で話した | 解き終えたコードを見ながら、英語で説明を録音した |
| 解いた回として数えるか | **数える**。復習ログに 1 行足し、REVIEW.md に反映される | **数えない**。復習ログには触らない |
| 話者 | Interviewer / Candidate に分ける | 本人だけ |
| レビュー | 面接の観点 + 英語の観点 | 説明の観点 + 英語の観点 |

## 最優先のルール

- 記録の `## 自分の振り返り` は本人の欄。問題 README の `## 考えたこと / アプローチ` と同じく、
  **中身を書かない**（提案・要約・清書・補完もしない）。ユーザーが明示的に頼んだときだけ書く。
- **トランスクリプトの英語を直さない。** 直してよいのは音声認識の誤りだけ。
  文法の誤り、不自然な言い回し、"um" "uh" "like" などのつなぎの言葉、言い直しは、
  英語のレビューの材料なのでそのまま残す。レビューの節で指摘する。

## 0. 情報を集める

足りないものはまとめて 1 回で聞く。

- **種類**: mock か solo か
- **問題**: 番号（タイトル）。repo に無ければ初回の記録が要る（mock の場合は 1. へ）
- **文字起こし**: ボイスメモアプリの文字起こしを貼ってもらう
- mock のみ: **面接官の名前**、**自力**（◎ ○ △ ×。面接官のヒントで進んだなら △）、
  **結果**（AC / WA / giveup など）、**所要時間**、**書いたコード**、面接官からのフィードバック（あれば）
- solo のみ: 説明したのが今の `solution.py` か（違えば、どの回のコードか）

## 1. mock の場合: 解いた回として記録する

mock は解き直し（または初回）の 1 回なので、先に `/leetcode-log` の手順で記録する。

- 初回 → `new_problem.py`（`--recall` 付き）。solution.py・テスト・README まで `/leetcode-log` どおり
- 解き直し → `new_attempt.py <番号> --recall <自力> --result <結果> --minutes <所要時間> --note "mock（面接官: <名前>）"`
  のあと、solution.py を mock で書いたコードで上書きし、前回との差分を見る

mock で書いたコードは、途中で止まったものや間違っているものもそのまま入れる。

## 2. 記録の雛形を作る

```bash
python scripts/new_english.py <番号> mock --interviewer <名前>
python scripts/new_english.py <番号> solo
```

`english/<日付>-<種類>.md` ができ、問題 README の `## 英語での説明` にリンクが足される
（古い README で節が無ければ作られる）。mock のときは復習ログの今日の行のメモ欄にもリンクが入る。
記録のファイルがエディタで開くので、`--no-open` は付けない（本人が振り返りを書けるように）。
手で `english/` を作らないこと。

## 3. 文字起こしを整形する

1. 貼られた文字起こしを、`## 元の文字起こし` の ```` ```text ```` ブロックに**一字一句そのまま**入れる
2. 整形したものを `## トランスクリプト` に書く
   - 直すのは音声認識の誤りだけ。例: "mono tonic stack" → "monotonic stack"、"pop" が "Pope" になっている、など。
     問題とコードの内容から、明らかに聞き間違いと判断できるものに限る
   - 誤認識か本人の言い間違いか判断できない箇所は、元のまま残して `[?]` を付ける
   - 文の切れ目と段落は読みやすく整えてよい（句読点を足すのは可。単語は変えない）
   - mock: 話者を推測して `**Interviewer:**` / `**Candidate:**` に分ける。ボイスメモには話者の区別が無いので、
     前後の流れから判断したことを報告で伝え、確認してもらう
   - solo: 話者分けはしない。話の区切りごとに段落を分ける

## 4. レビューを書く

指摘は必ず**トランスクリプトの実際の発言を引用**して具体的に書く。一般論だけで終わらせない。
良かった点も書く（次も続けるべきことが分かるように）。

**mock: `## レビュー: 面接の観点`**

- 問題の確認: 入力の制約や境界（空配列、重複、負の数など）を質問したか
- 方針を話してから書き始めたか。素直な解き方 → 改善、の流れを見せたか
- 書いている間も考えを口に出していたか。長い沈黙はどこか
- ヒントへの反応: すぐに取り込めたか、面接官の意図を確認したか
- 書き終えたあと、例を使って自分でコードを追ったか
- 計算量を聞かれる前に言えたか、根拠を説明できたか

**solo: `## レビュー: 説明の観点`**

- 順番: 問題の言い換え → 素直な解き方と問題点 → 核のアイデア → アルゴリズム → 例で追う → 計算量 → 境界ケース。
  どれが抜けたか、どこで順番が崩れたか
- コードを 1 行ずつなぞっているだけになっていないか。「なぜそうするのか」を言えたか
- 問題 README の「学び」の節にある要点（例: 84 なら「pop した棒の左端を引き継ぐ理由」）を説明できたか

**共通: `## レビュー: 英語の観点`**

- 表に「言ったこと / より自然な言い方 / 理由」を並べる。量より質で、**繰り返し出る癖を優先**する
- 技術的な言い回し（"iterate over", "pop from the stack", "in the worst case", "amortized" など）の誤用や、
  面接でよく使う定型句（"Let me make sure I understand the problem", "Can I assume ...?",
  "Let me walk through an example"）の言い換えの提案を含める
- つなぎの言葉が多い箇所、文が長すぎて伝わりにくい箇所も指摘する

mock で面接官からのフィードバックを聞いていれば、`## 面接官からのフィードバック` に言われたとおり書く。
概要の行（所要時間・結果・長さ）も埋める。

## 5. 次回やることと台本

- レビューで見つかった課題のうち、次にその問題を解くとき・話すときに試すことは、
  問題 README の `## 次回やること` に `- [ ] ...` で足す（REVIEW.md に載る）
- どの問題でも使える言い回しや説明の型が見つかったら、ルートの `talk-scripts/` に足すことを提案する。
  ユーザーが同意したら足す（フォルダが無ければそのとき作る）。勝手に作らない

## 6. 一覧を更新してコミット

```bash
python scripts/update_index.py
git add -A && git commit -m "<番号>. <タイトル> (mock)"      # mock。解き直しなら "(<N>回目, mock)"
git add -A && git commit -m "<番号>. <タイトル> (英語で説明)"  # solo
```

## 7. 報告する

- 保存した場所
- 整形で直した主な箇所と、`[?]` を付けた箇所（mock なら話者分けの確認のお願いも）
- レビューの要点を 3〜5 行（面接・説明の観点と英語の観点をそれぞれ最優先のもの）
- `## 自分の振り返り` が空なので本人に書いてもらうこと
