## 問題の要約

**昇順に並んだ**配列から、足して `target` になる 2 つの要素の位置を **1 始まり**で返す。答えはちょうど 1 組。
追加の空間は O(1) にすること（[1. Two Sum](../../arrays-hashing/0001-two-sum) のように dict を使うのは条件違反）。

## 計算量

- 時間: **O(n)** — 1 回ごとに `left` か `right` のどちらかが 1 つ内側へ進むので、合計で n 回以下
- 空間: **O(1)** — 添字 2 つだけ

## 学び・再利用できるパターン

### 並んでいるなら、ハッシュの代わりに両端から寄せる

[1. Two Sum](../../arrays-hashing/0001-two-sum) は並んでいない配列なので、「足りない分」を dict で引いた（空間 O(n)）。
この問題は**昇順に並んでいる**ので、dict を使わずに 2 ポインタで解ける（空間 O(1)）。

| | 1. Two Sum | 167. Two Sum II |
| --- | --- | --- |
| 配列 | 並んでいない | 昇順 |
| 方法 | dict で「足りない分」を引く | 両端から寄せる 2 ポインタ |
| 空間 | O(n) | **O(1)** |

### なぜ答えを飛ばさないのか

`numbers[left] + numbers[right] < target` のとき、`left` を右へ動かす。
このとき捨てているのは「`left` と、`right` より左のどれか」の組。
`right` が今いちばん大きい値なので、`left` と組んで target に届かないなら、それより小さい相手と組んでも**絶対に届かない**。
だから `left` はもう答えに使われないと分かり、安心して捨てられる。

和が大きすぎるときは、逆に `right` が答えに使われないと分かる。
**並んでいるおかげで、1 回の比較で片方を候補から確実に外せる**のが、この方法が O(n) になる理由。
[125](../0125-valid-palindrome) と同じ「両端から寄せる」形で、
このあとの 15 3Sum（1 つを固定して、残りでこの問題を解く）や 11 Container With Most Water もこの形になる。

### 細かい点

- `while` の条件と中の `if` / `elif` で、`numbers[left] + numbers[right]` を 3 回計算している。
  ループの先頭で `total = numbers[left] + numbers[right]` と 1 回だけ計算すると読みやすい
- `elif target < …` は、`<` でも `==` でもない残りなので `else` で足りる（`==` は `while` の条件で抜けている）
- 答えが必ず 1 組あるので `left < right` が崩れることはないが、`while` の条件に入れておくのは安全な書き方
